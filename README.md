## Краткое описание
Базовая реализация многокомпонентной системы для поиска музеев.

**Технологический стек:**  
Spring Boot, WebFlux, Spring MVC, MongoDB, Redis, Spring Security, JWT, Telegram Bot API, Docker.

---

## Текущая структура проекта

### **auth-service**
- Авторизация (логин админов по паролю)
- Выдаёт JWT

### **museum-service**
- Реактивный сервис (WebFlux + MongoDB + Redis)  
  *Redis — на этапе внедрения, заменит кэширование в боте*
- Публичные API: `/api/public/**` — запросы из бота или веб-приложения (не сделано), основной поиск
- Админские API: `/api/admin/**` — CRUD операции для админа, расширенный поиск с фильтрами (JWT required)

### **admin-backend-service**
- Spring MVC + Thymeleaf  
  *Реализовано базовое отображение и редактирование, поиск и фильтры в работе*
- Админский UI: `/museums/**`, `/login`, `/logout`
- Для CRUD операций обращается к museum-service

### **telegram-bot-service**
- Telegram Bot API клиент  
  *Пока обработка запроса выполняется напрямую в боте, кэширование временно тоже*
- Вызывает museum-service через REST  
  *Передача координат по кнопке или в текстовом виде*

### **api-gateway**
- Центральная точка входа
- Проксирует запросы:
    - `/auth/**`, `/.well-known/**` → **auth-service**
    - `/api/public/**` → **museum-service**
    - `/api/admin/**` → **museum-service** (JWT required)
    - `/museums/**`, `/login`, `/logout`, `/css/**`, `/js/**` → **admin-backend-service**

### **museum-contracts**
- Общий модуль с DTO и контрактами между сервисами  
  *Ведётся перенос всех общих DTO*

## Архитектура поиска и кэширования

### Производительный поиск с Redis

**Инициация поиска (тяжёлый запрос):**
1. Пользовательский запрос (текст/координаты) поступает на единый POST-эндпоинт.
2. *Integration Flow* определяет тип запроса и выбирает стратегию поиска (гео-поиск, по названию, по тегу, по городу и т.д.).
3. Выполняется основной запрос к MongoDB, возвращающий список ID найденных музеев.
4. Результат (список ID) сохраняется в Redis под уникальным `searchId` с коротким TTL.
5. Клиенту возвращается `searchId` и первая страница данных.

**Быстрая пагинация (лёгкий запрос):**
- Клиент делает GET-запрос с `searchId`.
- Сервис обращается в Redis, извлекает нужную порцию ID и возвращает результат без повторного обращения к БД.

**Оптимизация UI (через callback_data):**
- Информация о музее сериализуется, сжимается и кодируется, чтобы уложиться в лимиты Telegram API.
- Бот восстанавливает объект локально, что позволяет показывать детали без дополнительных запросов к API.
